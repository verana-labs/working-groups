# Post Quantum WG — 2026-11-04

## Agenda

- Askar API work for ML-DSA and the optional build flag
- Independent test suite hosted on a personal repository
- Python and JavaScript wrappers; start of Credo work
- ML-DSA key and signature sizes, parameter set choice
- Impact on the ledger / Cosmos SDK
- Alternatives to ML-DSA (Falcon) and maturity of the field
- Selective disclosure, unlinkability and BBS+
- Communication about the work

## Discussion

**Askar API and optional flag.** Martin Evain reported progress on the Askar API, with several small changes. He agreed with the earlier view that ML-DSA support should remain optional, but for now the MLDSA flag was enabled by default in the CI builds and releases, as he was unsure how to exclude it cleanly. He had raised the point as a question for Andrew, to find out whether that is acceptable or whether the default should be removed. The dependencies and wiring for the new code path were in place.

**Tests.** Martin had built a separate test project on his own GitHub, comparing the Rust implementation against an independent implementation (noble), including both randomised and deterministic signature variants, and had found and reported several issues on the Askar repository. He asked whether linking to an external test repository from a pull request was acceptable, as he did not want to add a large test bundle to Askar itself. Ariel Gentile said the tests in the Askar repositories were fairly limited, encouraged adding the links in the pull request, and suggested that later the tests could be moved either into the Askar repositories or into the Open Wallet Foundation organisation, and extended to other Askar crypto tests.

**Wrappers and Credo.** Martin said the Python wrapper worked by importing the commit, and that he had also adapted the JavaScript wrapper, with a less complete test setup. He had started work on Credo using his local JavaScript Askar build, but nothing was working end to end yet. Ariel asked whether Python would come first; Martin proposed doing both wrappers at the same time, and Ariel agreed this would be more practical, noting that Andrew would probably want to test with the wrappers.

**Sizes and parameter sets.** In answer to a question from Fabrice Rochette, Martin gave signature sizes of roughly 2428, 3309 and 4627 bytes for the different ML-DSA variants, with ML-DSA-65 (around 3309) as the likely default. He described the trade-off between security level, signing time and signature size, suggesting that issuers signing many credentials might prefer 44 while long-lived documents such as passports might justify 87, and said benchmarks were needed on production impact. He noted that keys can be regenerated from a 32-byte seed. On performance, he said ML-DSA is slower than Ed25519 (around ten times for verification, less for signing, roughly 300 microseconds) but faster than RSA in some cases.

**Ledger impact.** Fabrice said credential size was not his concern, but the blockchain was, since every block is signed by all validators. He cited figures of 64 bytes signature / 32 bytes public key today versus about 1252 bytes public key and roughly 3 kB signature, giving a move from 10–15 kB to around 500 kB per block for 150 validators, about 7 GB per day, and 350 GB per year with 20 validators. He considered this manageable, since old blocks can be pruned and storage keeps improving, but said the impact on the ledger and on Cosmos address size still had to be checked. Ariel suggested looking at how this was handled in the Cosmos SDK.

**Alternatives and maturity.** Martin mentioned Falcon as an alternative with slower signing and verification but signature sizes roughly three times smaller (around 1400 bytes for Falcon-512 versus 3800 for ML-DSA-44). Fabrice said the field is not mature and the current work is experimental; the value is in proving the full pipeline works, after which another algorithm can be added easily.

**Privacy properties.** Fabrice asked whether presentations are linkable. Ariel said this depends on which attributes are disclosed, and that zero-knowledge proofs normally allow attributes to be presented without revealing the source credential. Martin noted that selective disclosure is possible and that several signatures can be issued for the same credential to avoid reusing one signature across verifiers. Ariel proposed BBS+ with post-quantum signatures as a possible topic for January.

**Communication.** Fabrice encouraged publishing on social media once there are concrete results, including the fact that the team contributed ML-DSA support to Askar and Credo. Ariel agreed to publish once the Credo work is demonstrable, even if experimental.

## Decisions

- ML-DSA support in Askar is to remain optional; the default build flag stays as is pending Andrew's answer.
- Links to Martin's external test repository will be added in the pull request rather than importing the tests into Askar for now.
- The Python and JavaScript wrappers will be done together rather than sequentially.
