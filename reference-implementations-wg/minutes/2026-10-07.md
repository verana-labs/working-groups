# Reference Implementation WG — 2026-10-07

## Agenda

1. DIDComm v2 PR review feedback and Trust Ping support in Credo
2. Specification writing practice (functional spec vs. system design)
3. Playground: personal wallets integration and conformance testing
4. Playground / test net migration to V4 and basic use cases
5. DIDComm v2 connection establishment issue (concurrent first messages)
6. VS-Agent, Indexer and Frontend spec-compliance gaps; TRQP endpoints
7. Wallet forks, app stores and upstreaming
8. Deployment repo simplification

## Discussion

**Credo DIDComm v2 PR** Ariel Gentile and Tarun Vadde discussed review comments received on the DIDComm v2 work. Ariel accepted that most of the raised points were valid and should be fixed, but objected to re-architecting the module, citing the issue-credential module in Credo, whose abstract protocol interfaces created type complexity and a difficult setup experience while no new issue-credential protocol has appeared in four years. He said he had replied that he would welcome a cleaner architecture proposal at the moment only if it would be possible to merge to main within one month. Tarun agreed that the pursuit of perfect clean code had delayed simple features for years.

**Specification practice.** Ariel described an experiment on an unrelated personal project (a ham-radio logging website), splitting documentation into a one-line-per-requirement functional specification and a separate system design document containing database and technical constraints. He suggested a similar approach for the V5 specifications, while acknowledging the Verana system is far more complex.

**Playground wallets.** Maxime Mansiet reported that the integrated wallets (Hologram, WWWallet, Inji, EUDI, Swiss) are all working. He plans to keep a set of main wallets visible on the playground with an expandable card for additional ones. He integrated an "EUDI dev testing suite" repo (shared on Discord) into CI and opened a PR on the specifications describing how conformance testing should work. More wallets are supported than on the test net; the Hologram implementation still needs finishing.

**V4 migration.** Ariel is working on a V4 branch of the playground, aiming to replace the current test net rather than migrate existing objects, ideally before the end of the week. The personal-wallet aggregated issuer/verifier examples work; of the four basic use cases, Vesta, the crypto exchange and Verandia appear deployed (not yet verified by hand), while "Better Hiring Institute" still has workflows to fix.

**DIDComm v2 connection handling.** Ariel explained that in DIDComm v2 a connection is established by the first message, whatever it is. When a client (e.g. Hologram) sends two messages almost simultaneously (discover-features query and profile request) to a public DID, the receiving agent can create two connections, especially in multi-instance deployments. He observed this in testing. A possible client-side convention is to send a Trust Ping first and wait for the response before sending anything else; Tarun said he had assumed this behaviour already. Ariel conceded this is opinionated and not required by the spec, but argued it is practical and also verifies the other end is reachable, since trust resolution only queries the indexer endpoint. He raised whether Credo needs additional connection states (the current RFC-derived states being inaccurate) and proposed discussing it further.

**Spec compliance.** Andres Vallecilla opened an issue on missing VS Agent endpoints and found further gaps in the indexer, two of which he considered important; Patrick has started work on them. Frontend gaps exist but he wants to review before filing issues. Ariel asked that Maxime's non-essential PRs be marked draft rather than closed. He also flagged that the TRQP endpoints are untested and should become the preferred mechanism for third-party wallet integrations, at least for accreditation checks.

**Wallet forks and stores.** Maxime works via personal forks and pull requests; the changes are mainly UI (the Verana trusted/untrusted card). Fabrice asked for Play Store/App Store versions for business demos, as some users will not install APKs. Ariel said publishing clones to the stores would likely be rejected and that upstreaming to wallet maintainers is the long-term goal; Inji is considered likely to accept a PR. One wallet (native Swift/Kotlin) has no fork in the organisation yet.

**Deployment.** Andres asked for review of a PR in the deploy repo that simplifies deployment.

## Decisions

- The current test net will be replaced by a new V4 testnet rather than migrating existing objects.
- Non-essential open PRs from Maxime will be marked as drafts, not closed.
