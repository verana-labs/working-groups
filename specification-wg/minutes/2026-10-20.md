# Specification WG (SPEC-WG) — 2026-10-20

## Discussion

**Merge sequence.** Fabrice Rochette explained that he had commented on and opened a PR against the economic model PR authored by Pratik, answering the questions he could. The plan was to merge PR 183 into 177, bring the package into main, and then rebase the remaining PR.

**New credential schema attributes.** Fabrice walked through the additions to the credential schema in the v5 data model: a `subject kind` indicating whether a credential may be issued to a service or to a person; a `presentation mode` with three values for service subjects — public (presented in the DID document), accredited automatic (the agent must present on request from an accredited verifier) and accredited approval (the service controller must approve each presentation); a restriction on credential formats/containers per schema; a flag for whether a digest must be anchored on chain (needed for AnonCreds, optional for SD-JWT, which can rely on a separate revocation list, and relevant later for mDoc); a `verification session` flag stating whether the create/update session call is mandatory when fees are zero; and a `presentation validity period` allowing a governance framework to require re-requesting (and re-paying for) a credential after a set time, with the presentation digest anchored on chain as legal proof.

**Debate on presentation modes.** Ariel Gentile questioned why the automatic/approval distinction belongs on chain rather than being internal service configuration, arguing it cannot be proven whether an agent answered automatically or asked its controller, and that the names "accredited automatic" and "accredited approval" were poor. Fabrice argued the rule must be enforceable by the ecosystem and defined immutably in the schema, since some credentials are legally mandatory to present while others should remain at the holder's discretion, like a personal wallet. He compared non-compliance to not publishing mandatory public credentials — a slashing risk. Fabrice said he had no objection to renaming the attributes and asked Ariel to reflect and come back the following week with concrete proposals. Ariel also warned that the credential schema object is accumulating too many parameters and that overlapping terminology (credential schema, JSON schema) makes the spec hard to read.

**Presentation digest anchoring.** Fabrice described the flow: the presenter computes and shares the digest of the presentation so the verifier can anchor it when creating the session and paying, after which the presenter releases the credential. The verifier cannot be asked to pay after receiving the credential. The open edge case is a presenter computing the digest incorrectly; an escrow-based solution was considered but judged too complex. Ariel noted that a presentation may contain more than one credential, which is not used today but will matter later; Fabrice said it would be limited to one credential per presentation for now, and that reducing the number of transactions per service remains to be optimised.

**v4 and other changes.** v4 contains bug fixes only. Other items: digest holder and participant ID added so revocation can be limited to the issuing service; slashed ecosystem participants no longer receive fees, reducing the verifier's price; an indexer issue clarifying that an anchored digest keeps a credential valid after the issuer entry becomes inactive, whereas AnonCreds credentials do not; and matching updates in the Verifiable Trust spec, for which Fabrice asked Ariel to verify the container/format explanations.

**Removed feature and onboarding.** The mechanism defining who may request which credential attributes was removed from v5 as too complex for current needs. Both noted that the holder permission is created before credential issuance, requiring the receiving agent to call the trigger resolver, and agreed this needs rethinking later.

**Spec duplication.** Ariel observed that anchoring rules are defined both in the Verifiable Trust spec and in the VPR data model, and proposed defining them once (in VT) with the other referencing it, keeping only the checks in the VPR spec. Fabrice agreed and said he would remove the duplicated credential schema section; he mentioned a single repository as an option but noted it has implications.

**Work in progress.** Fabrice is working on corporation sponsorship, so public entities never handle or see the token, and on a per-transaction gas cap to prevent a compromised service from draining a corporation's wallet. These PRs stay in draft.

**Martín.** Fabrice met Martín and settled the monthly payment arrangement; Martín was encouraged to gain autonomy and join the working groups. Ariel reported his comments were well received by the Askar maintainers, who updated dependencies to enable the post-quantum work, and that Credo is also involved.

## Decisions

- Merge order agreed: PR 183 into 177, then into main, then rebase the remaining PR.
- Attribute names in the credential schema are open to change; the logic is what Fabrice asked to be reviewed first.
- Presentations will be limited to one credential for now.
- The attribute-level request permission feature is removed from v5.
- Rules will be defined in a single spec and referenced from the other; the duplicated credential schema section will be removed from the VPR spec.
